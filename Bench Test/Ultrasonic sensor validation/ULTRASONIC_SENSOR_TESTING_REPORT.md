## 1. Objective

The primary objective was to perform bench-level functional verification and electrical integration of the **HC-SR04 ultrasonic distance sensor** with the ESP32 microcontroller subsystem before proceeding to full multi-sensor array deployment.

The specific testing objectives were:

1. **Electrical Integration**: Verify physical and electrical interfacing between the HC-SR04 and the ESP32-WROOM-32D development board.
2. **5 V Power Verification**: Verify the sensor's specified 5 V operating power requirement.
3. **Signal Integrity**: Verify the physical paths and timing of the `TRIG` (trigger pulse) and `ECHO` (echo pulse) lines.
4. **Voltage Divider Interface**: Validate a resistive level-shifting voltage divider to safely step down the 5 V `ECHO` pulse to ESP32 3.3 V logic levels.
5. **Firmware Acquisition**: Verify the ESP32 firmware driver (`HCSR04Driver` and `HardwareUltrasonicIO`) in measuring pulse duration and calculating distance in millimeters.
6. **Boot/Flash Fault Isolation**: Investigate, troubleshoot, and isolate bootloader reset loops and flash-read errors (`flash read err, 988`) observed when powering the sensor directly from the ESP32 5 V power rail.
7. **External 5 V Power Validation**: Verify sensor operation and ESP32 boot stability using an isolated, external 5 V power supply.
8. **Signal Response**: Verify that the sensor generates valid pulse widths corresponding to physical targets.
9. **Live Dynamic Tracking**: Verify that the sensor dynamically detects a moving target (human hand) and reports changing distances across multiple stationary positions.
10. **Baseline Subsystem Status**: Establish the verified functional baseline of the single-sensor implementation before designing multi-sensor arrays or obstacle-avoidance logic.

## 2. Hardware Used

The bench testing and troubleshooting were conducted using only the following physical hardware components:

* **Microcontroller Board**: ESP32-WROOM-32D Development Board (30-pin NodeMCU form factor, 4MB Flash).
* **Ultrasonic Sensor**: HC-SR04 Ultrasonic Distance Sensor Module (dual piezoelectric transducers, 40 kHz).
* **External 5 V Bench Power Source**: Raspberry Pi 4 Model B (utilizing GPIO Header Physical Pin 2 for 5 V power and Physical Pin 6 for Ground during isolated supply testing).
* **Development Computer & Host Link**: Development laptop connected to the ESP32 via standard USB-UART cable (`/dev/cu.SLAB_USBtoUART` / CP2102 bridge) providing ESP32 power and serial monitor communication at 115200 baud.
* **Prototyping Medium**: Solderless breadboard.
* **Passive Components**: Through-hole carbon-film resistors ($4.7\text{ k}\Omega \pm 5\%$) for signal level-shifting.
* **Interconnects**: Standard male-to-male and male-to-female DuPont jumper wires.

> [!NOTE]
> During all successful signal and tracking tests, the ESP32 was powered via USB from the development computer, while the HC-SR04 was powered via an isolated 5 V supply rail.

## 3. HC-SR04 Electrical Requirements

Based on manufacturer documentation and verified datasheet specifications, the HC-SR04 sensor imposes the following electrical requirements:

| Parameter | Specification | Project Application Notes |
|---|---|---|
| **Operating Voltage ($V_{CC}$)** | $5.0\text{ V DC}$ | **Mandatory**. Sensor circuitry is designed and specified for 5 V operation. |
| **Quiescent Current** | $< 2\text{ mA}$ | Standby current draw. |
| **Operating Current** | $\sim 15\text{ mA}$ (up to $30\text{ mA}$ burst) | Transducer burst acoustic drive current. |
| **Trigger Input (`TRIG`)** | $10\ \mu\text{s}$ TTL Pulse (`HIGH`) | Generated by ESP32 GPIO. |
| **Echo Output (`ECHO`)** | $5.0\text{ V}$ TTL Pulse Width | Must be level-shifted before entering ESP32 GPIO. |
| **Acoustic Frequency** | $40\text{ kHz}$ | Ultrasonic transducer burst frequency. |
| **Minimum Effective Range** | $\sim 20\text{ mm}$ ($2\text{ cm}$) | Hardware physical blind zone. |
| **Maximum Effective Range** | $\sim 4000\text{ mm}$ ($400\text{ cm}$) | Acoustic attenuation limit. |
| **Measuring Angle** | $\sim 15^\circ$ conical | Effective beam width. |
| **Distance Formula** | $\text{Distance (mm)} = \frac{\text{Pulse Width (}\mu\text{s)} \times 0.343}{2}$ | Speed of sound in air ($343\text{ m/s}$ at $20^\circ\text{C}$). |

> [!IMPORTANT]
> The HC-SR04 module documentation specifies a **5 V DC power supply**. The module was not powered from 3.3 V in this validated configuration.

## 4. Final Known-Good Wiring

The authoritative, known-good physical bench wiring that successfully demonstrated sensor functionality is documented below:

### 4.1 Sensor Interconnects

| Sensor Pin | Physical Destination | Signal Function | Voltage Level |
|---|---|---|---|
| **`VCC`** | Raspberry Pi 4 Physical Pin 2 | DC Power Supply | $5.0\text{ V DC}$ |
| **`GND`** | Breadboard Common Ground Rail | Ground Reference | $0\text{ V}$ (Common) |
| **`TRIG`** | ESP32 `GPIO4` (Header Pin `4`/`D4`) | Trigger Input | $3.3\text{ V}$ TTL Logic |
| **`ECHO`** | Voltage Divider Input Resistor | Echo Output | $5.0\text{ V}$ Pulse |

### 4.2 ECHO Voltage-Divider Configuration

Because the HC-SR04 `ECHO` output delivers a $5.0\text{ V}$ pulse, direct connection to an ESP32 pin would exceed the $3.6\text{ V}$ absolute maximum GPIO rating. A passive voltage divider is placed on the breadboard:

```text
HC-SR04 ECHO (5.0 V)
         │
         ▼
  [ 4.7 kΩ Resistor (R1) ]
         │
         ├───► ESP32 GPIO34 (Input-only, no internal pull resistors)
         │
  [ 4.7 kΩ Resistor (R2) ]
         │
         ▼
  Common GND Rail
```

* **Nominal Attenuation**: $\frac{R_2}{R_1 + R_2} = \frac{4.7\text{ k}\Omega}{4.7\text{ k}\Omega + 4.7\text{ k}\Omega} = 0.50$
* **Divided Voltage at GPIO34**: $5.0\text{ V} \times 0.50 = 2.50\text{ V}$
* **Logic Threshold Compliance**: $2.50\text{ V}$ exceeds the ESP32 $V_{IH(\min)}$ threshold ($0.75 \times V_{DD} \approx 2.475\text{ V}$) while remaining completely safe below $3.3\text{ V}$.

### 4.3 ESP32 Boot/Ground Interconnects

* **Common Ground**: ESP32 `GND` header pin is tied directly to the breadboard common ground rail with a dedicated jumper.
* **GPIO12 Strapping**: During troubleshooting, `GPIO12` (MTDI) was connected directly to the adjacent ESP32 `GND` header pin using a short dedicated jumper wire.

> [!NOTE]
> **`GPIO12` is NOT part of the HC-SR04 `TRIG` or `ECHO` signal path.** It was grounded exclusively to lock the ESP32 ROM boot strapping to `LOW` ($3.3\text{ V}$ flash regulator voltage).

## 5. Initial ESP32 5 V Power Test & Problem Identification

Initial bench tests attempted to supply the HC-SR04 $V_{CC}$ pin directly from the ESP32 board's onboard `5V` (`VIN`) header pin. This resulted in repeatable boot and flash-read failures.

### 5.1 Observed Behavior

* **Condition 1 (Sensor Disconnected)**:
  * PlatformIO firmware uploads succeeded 100% of the time.
  * ESP32 booted cleanly with ROM code `boot:0x13 (SPI_FAST_FLASH_BOOT)`.
  * Firmware executed setup and reached `AutoChair in IDLE` without errors.
  * Zero flash read errors were reported.

* **Condition 2 (Sensor Connected to ESP32 5V/VIN Rail)**:
  * Flash uploads failed during stub initialization with:
    `WARNING: Failed to communicate with the flash chip, read/write operations will fail.`
  * ESP32 entered an infinite bootloader reset loop emitting:
    ```text
    rst:0x1 (POWERON_RESET), boot:0x17 (SPI_FAST_FLASH_BOOT)
    flash read err, 988
    ets_main.c 384
    rst:0x10 (RTCWDT_RTC_RESET), boot:0x17 (SPI_FAST_FLASH_BOOT)
    flash read err, 988
    ```
  * In further isolation (Condition 3), the HC-SR04 had $V_{CC}$ connected to ESP32 `5V` and `GND` connected, while `TRIG` and `ECHO` were **completely disconnected**. Even with zero signal lines attached, the ESP32 repeatedly failed to boot with `flash read err, 988`.

### 5.2 Engineering Note on Root Cause
The tests established a repeatable, empirical association between powering the HC-SR04 from the ESP32 `5V`/`VIN` rail and the occurrence of `flash read err, 988`.

> [!IMPORTANT]
> The exact physical/electrical mechanism was not measured or conclusively identified because no oscilloscope or multimeter was available during this bench stage. Hypotheses such as power-rail transients, supply sag on the onboard AMS1117 regulator, ground-return offsets, or parasitic backfeeding remain unverified.

## 6. Systematic Isolation Test Sequence

To isolate whether the failure originated in firmware, strapping pins, signal lines, or the power rail, a controlled sequence of isolation tests was executed:

| Test ID | HC-SR04 $V_{CC}$ | HC-SR04 GND | TRIG (GPIO4) | ECHO (GPIO34) | GPIO12 | Boot Code | Flash Error 988 | Firmware State | Finding / Conclusion |
|---|---|---|---|---|---|---|---|---|---|
| **Test A** | Disconnected | Disconnected | Disconnected | Disconnected | Jumped to GND | `boot:0x13` | **NO** | `IDLE` (PASS) | Baseline: Bare ESP32 boots and executes firmware reliably. |
| **Test B** | Connected to ESP32 5V | Connected | Connected | Connected via Divider | Jumped to GND | `boot:0x17` | **YES** | Boot Loop (FAIL) | Complete assembly fails boot when sensor is powered from ESP32 5V. |
| **Test C** | Disconnected | Connected | Disconnected | Connected via Divider | Jumped to GND | `boot:0x13` | **NO** | `IDLE` (PASS) | Passive ECHO divider on GPIO34 does not cause boot failure when sensor unpowered. |
| **Test D** | Disconnected | Connected | Connected | Connected via Divider | Jumped to GND | `boot:0x13` | **NO** | `IDLE` (PASS) | TRIG connection on GPIO4 does not cause boot failure when sensor unpowered. |
| **Test E** | Connected to ESP32 5V | Connected | Disconnected | Disconnected | Jumped to GND | `boot:0x13` / `0x17` | **YES** | Boot Loop (FAIL) | **Key Isolation**: Powering sensor from ESP32 5V fails even with zero signal pins attached. |

## 7. External 5 V Power Isolation Test

Following the result of Test E, the sensor power was moved to an independent external 5 V power rail supplied by an active Raspberry Pi 4:

* **Pi Physical Pin 2 ($5\text{ V}$)** $\rightarrow$ HC-SR04 $V_{CC}$
* **Pi Physical Pin 6 ($\text{GND}$)** $\rightarrow$ Breadboard Common Ground Rail
* **ESP32 `GND`** $\rightarrow$ Breadboard Common Ground Rail
* **HC-SR04 `GND`** $\rightarrow$ Breadboard Common Ground Rail
* **ESP32 USB** $\rightarrow$ Development Laptop (providing independent $3.3\text{ V}$ regulation)
* **Isolated Constraint**: Pi $5\text{ V}$ was **NOT** connected to the ESP32 `5V`/`VIN` pin.

> [!NOTE]
> This external power configuration was implemented strictly as a **bench diagnostic isolation test** to validate sensor signal processing and firmware acquisition. It does not represent the final AutoChair wheelchair power distribution architecture.

## 9. Firmware Driver Validation

The ESP32 firmware implementation was validated in real time during live operation:

1. **Architecture**:
   * `HardwareUltrasonicIO` generates a calibrated $10\ \mu\text{s}$ trigger pulse on `GPIO4`.
   * `pulseIn(GPIO34, HIGH, 30000)` measures the returning echo pulse duration with a $30\text{ ms}$ hardware timeout.
   * `HCSR04Driver` converts pulse width ($\mu\text{s}$) into physical distance ($\text{mm}$) using the acoustic propagation equation.
2. **Telemetry Output**:
   * Valid distance measurements are reported in millimeters with status code `status=2` (`SensorStatus::OK`).
   * Invalid/timeout conditions report `-1.0 mm` with appropriate failure statuses (`status=7` for `TIMEOUT`, `status=5` for `OUT_OF_RANGE`).

## 17. Final Engineering Conclusion

The HC-SR04 single-sensor subsystem has successfully completed bench-level functional integration testing. The sensor was interfaced with the ESP32 using `GPIO4` for `TRIG` and `GPIO34` for the `ECHO` signal stepped down through a $4.7\text{ k}\Omega / 4.7\text{ k}\Omega$ resistive voltage divider. The firmware driver successfully acquired echo timing pulses, calculated physical distances in millimeters, and emitted verified `status=2` (`SensorStatus::OK`) telemetry records.

During power-path investigation, supplying the HC-SR04 directly from the ESP32's onboard $5\text{ V}$ (`VIN`) header pin caused repeatable bootloader flash-read failures (`flash read err, 988`), even when all sensor signal lines (`TRIG` and `ECHO`) were disconnected. The exact electrical root cause remains unverified because voltage/current waveforms were not measured. The diagnostic bench isolation setup powered the HC-SR04 from an isolated $5\text{ V}$ rail (provided by a Raspberry Pi 4) with a common ground reference to the ESP32.

Under this isolated supply arrangement, the HC-SR04 operated with complete stability alongside the ESP32 firmware. Live dynamic tracking demonstrated that the sensor reliably tracked a human hand across 6 distinct positions ($90\text{ mm}$ to $130\text{ mm}$) over 30 consecutive samples with zero communication drops.

The preliminary $300\text{ mm}$ tests are not accepted as formal accuracy validations because reference distances were estimated rather than calibrated with precision fixtures. 

**Summary Assessment**:
* **HC-SR04 Single-Sensor Functional Testing**: **`PASS`**
* **Absolute Distance Accuracy Validation**: **`NOT YET VALIDATED`**
* **Multi-Sensor Integration**: **`PENDING`**
* **Final Wheelchair Power Architecture**: **`PENDING`**

## 18. Limitations and Next Steps

To maintain rigorous safety and validation standards for the AutoChair platform, the following sequential steps must be followed:

1. **No Redundant Single-Sensor Testing**: The basic single-sensor electrical interface and firmware driver are functionally proven; do not repeat basic single-sensor functional tests.
2. **Final Power Architecture Design**: Design and validate a dedicated, noise-isolated $5\text{ V}$ DC-DC power converter for the sensor array to prevent power-rail interference with the ESP32 core.
3. **Multi-Sensor Array Deployment**: Deploy sensors 1 through 5 on verified GPIO assignments.
4. **Sequential Polling Schedule**: Validate time-multiplexed sequential triggering ($50\text{ ms}$ stagger) in firmware to eliminate acoustic crosstalk between adjacent transducers.
5. **Acoustic Interference Characterization**: Measure physical sensor-to-sensor acoustic beam overlap on the wheelchair chassis.
6. **Precision Mechanical Calibration**: Mount sensors in rigid test fixtures and perform distance calibration curves against precision optical/ruler references.
